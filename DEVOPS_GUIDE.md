# DevOps-гайд по проекту (для тех, кто учится)

Этот документ объясняет, **зачем нужен каждый файл и папка** в проекте,
и **почему DevOps-инфраструктура устроена именно так**. Будет полезно, если
ты впервые имеешь дело с Docker, переменными окружения, портами и
горизонтальным масштабированием.

---

## 1. Общая картина (аналогия — колл-центр)

Представь колл-центр:

- **Координатор (диспетчер)** — один человек с тетрадкой. Он принимает
  заявки, раздаёт их операторам и записывает результаты.
- **Проберы (операторы)** — много людей с телефонами. Каждый спрашивает
  диспетчера «что у тебя есть?», получает задачу, выполняет, возвращает
  результат.
- **Заявка** — это «список VPN-ссылок + список сайтов, которые надо проверить».
- **Результат** — это «вот эта ссылка работает / не работает, вот эти сайты
  открылись через неё».

Главная идея: **один диспетчер, много операторов**. Операторы между собой
не общаются. Они общаются только с диспетчером. Поэтому добавить нового
оператора — просто запустить ещё один контейнер, ничего не меняя в других.

Эта схема называется «hub-and-spoke» (звезда). Она очень удобна в DevOps
потому что:
- можно убить любого пробера — координатор просто отдаст его задачу другому;
- можно добавлять/убирать проберы на лету;
- нет «горячих точек» — у всех проберов одинаковая конфигурация.

## 2. Почему два отдельных сервиса (а не одна программа)

Это базовый принцип: **separation of concerns** (разделение
ответственности). У нас две роли:

| Роль | Где должна жить? | Чувствительность |
| --- | --- | --- |
| Хранит данные (БД, история результатов) | На **одном** надёжном сервере с бэкапами | Высокая — потеря = потеря всей истории |
| Тестирует VPN-ссылки | На **многих** дешёвых серверах в разных странах | Низкая — упал, перезапустил, всё ок |

Если бы это была одна программа — пришлось бы держать «надёжность» на всех
N серверах. А так у тебя **один маленький, но защищённый координатор**
(например, на VPS с бэкапом) и **N одноразовых проберов**, которые можно
перезагружать когда угодно.

В индустрии этот шаблон зовётся **stateful vs stateless**:
- `coordinator` — **stateful**: у него есть БД, которую нельзя потерять.
- `prober` — **stateless**: у него ничего нет, всю историю он отправляет в координатор.

> 💡 **Правило DevOps:** stateful-сервисов должно быть как можно меньше.
> Stateless-сервисы можно множить, перемещать, убивать без последствий.

### Принцип «один сервис = одна папка = один Dockerfile»

Каждый отдельно деплоимый компонент живёт в своей папке с собственным
`Dockerfile`. Так делают почти все большие проекты. Когда у тебя
вырастет третий сервис (например, «генератор отчётов»), ты просто
создашь папку `reporter_service/` рядом с `prober/` и `coordinator/`.

### Почему `pyproject.toml` один общий

Потому что оба сервиса написаны на Python и шарят почти все библиотеки
(FastAPI, httpx, pydantic). Если бы они были на разных языках — у каждого
была бы своя описалка зависимостей. В большом проекте часто делают
**монорепо** (как у нас) либо **полирепо** (каждый сервис в отдельной git-репе).
Для маленькой команды монорепо проще.

## 4. Что такое Dockerfile (и зачем он)

`Dockerfile` — это **рецепт**, по которому строится **образ** (image).
Образ — это «замороженная» файловая система с твоей программой и всеми
зависимостями.

Открой `prober/Dockerfile` — там по шагам:

```dockerfile
FROM python:3.12-slim          # Начинаем с готового образа Python
RUN apt-get install openvpn …  # Доустанавливаем системные пакеты
RUN curl … sing-box.tar.gz     # Скачиваем sing-box
COPY pyproject.toml ./         # Кладём метаданные
COPY prober ./prober           # Кладём код
RUN pip install .              # Ставим зависимости
EXPOSE 8090                    # Документируем, что слушает порт 8090
CMD ["python", "-m", "prober.main"]  # Что запускать при старте
```

**Правило:** Dockerfile должен быть **самодостаточным** — клонируешь репу
на новый сервер, делаешь `docker build`, и оно работает. Никаких
«а ещё надо вручную поставить X». Если что-то нужно — впиши в Dockerfile.

> 💡 Из образа создаются **контейнеры**. Можно запустить много контейнеров
> из одного образа — они изолированы друг от друга. Образ = класс,
> контейнер = объект.

## 5. Что такое docker-compose.yml (и почему он удобен)

Файл `docker-compose.yml` описывает **систему из нескольких контейнеров**.
Вместо того чтобы запускать каждый `docker run …` руками, ты пишешь:

```yaml
services:
  coordinator:
    build: { dockerfile: coordinator/Dockerfile }
    ports: ["8080:8080"]
    volumes: ["coordinator-data:/app/data"]

  prober-1:
    build: { dockerfile: prober/Dockerfile }
    depends_on: [coordinator]
```

…и одной командой `docker compose up -d` поднимаешь **обе** программы
сразу. Compose сам:
- создаёт общую виртуальную сеть для контейнеров;
- даёт им имена-DNS (внутри контейнера `prober-1` адрес координатора —
  просто `http://coordinator:8080`, никаких IP);
- следит, чтобы координатор стартовал раньше пробера (`depends_on`);
- автоматически перезапускает упавшие контейнеры (`restart: unless-stopped`).

**Когда уже не хватит docker-compose?** Когда серверов станет много (десятки).
Тогда смотришь в сторону **Kubernetes** или **Nomad**. Но это уже следующий
уровень — большинство стартапов годами живут на чистом compose.

## 6. Переменные окружения (env) — где и как

**Правило:** код всегда одинаковый, **отличия между окружениями (dev / prod)
живут в переменных окружения**. Это называется
[«The Twelve-Factor App»](https://12factor.net) — это must-read для DevOps.

В нашем проекте:

1. `.env.example` — **шаблон** с описанием всех переменных и заглушками.
   Этот файл коммитится в git, чтобы человек, клонировавший репу, видел,
   что нужно заполнить.
2. `.env` — **твои реальные значения** (токены, URL координатора). **НЕ
   коммитится** (есть в `.gitignore`). Docker-compose читает его автоматически.
3. `prober/config.py` и `coordinator/config.py` — Python-код, который читает
   эти переменные через `pydantic-settings` и превращает в типизированные
   настройки.

### Какие переменные у нас и зачем

| Переменная | Кто её читает | Зачем |
| --- | --- | --- |
| `COORDINATOR_API_TOKENS` | координатор | Список токенов, которые могут регистрировать проберы и слать результаты |
| `COORDINATOR_ADMIN_TOKEN` | координатор | Токен для админа, чтобы создавать джобы и открывать дашборд |
| `COORDINATOR_DB_URL` | координатор | Где лежит SQLite-файл (или Postgres URL, если переедешь) |
| `COORDINATOR_URL` | пробер | Куда пробер ходит за задачами |
| `PROBER_API_TOKEN` | пробер | Его токен для авторизации в координаторе |
| `PROBER_NAME` | пробер | Уникальное имя — чтобы их различать в дашборде |
| `PROBER_LOCAL_SOCKS_PORT` | пробер | Локальный порт, на котором sing-box слушает |
| `PROBER_SITE_TIMEOUT` | пробер | Таймаут одного HTTP-запроса |
| `PROBER_LINK_TIMEOUT` | пробер | Таймаут на всю проверку одной ссылки |

### Где хранить секреты в проде

В порядке возрастания серьёзности:
1. **`.env` файл на сервере, права 600** — для одного маленького VPS пойдёт.
2. **`docker secrets`** — встроено в Docker Swarm; файл монтируется в
   `/run/secrets/...`.
3. **HashiCorp Vault / AWS Secrets Manager / etc.** — когда инфраструктура
   действительно большая.

Главное: **никогда не коммить секреты в git**. Если случайно закоммитил
— токен **уже скомпрометирован**, нужно перевыпустить, а историю — переписать.

## 7. Порты — что куда подключается

Тут многие путаются. Запомни:

```
┌──────────────────────────┐
│         Хост-машина       │
│                          │
│  :8080 ─────┐            │  ← пользователь видит этот порт снаружи
│             │            │
│  ┌──────────▼──────────┐ │
│  │  Контейнер coord.   │ │
│  │      слушает :8080  │ │
│  └─────────────────────┘ │
│                          │
│  ┌─────────────────────┐ │
│  │  Контейнер prober   │ │
│  │      :10808 internal│ │  ← порт sing-box внутри пробера
│  └─────────────────────┘ │  ← снаружи НЕ маппится, не нужен
└──────────────────────────┘
```

В `docker-compose.yml`:

```yaml
ports:
  - "8080:8080"   # host_port:container_port
```

— «открой порт 8080 наружу хоста, перенаправь на порт 8080 в контейнере».

**Внутри одной compose-сети** (между нашими контейнерами) проброс портов
не нужен. Пробер обращается к координатору как `http://coordinator:8080`
— это работает потому, что compose сам подняла DNS, а `:8080` — это
порт, который слушает сервис **внутри своего контейнера** (не маппинг!).

> 💡 Если ты выставил `ports: ["8080:8080"]` — этот порт **смотрит в интернет**
> на твоём VPS. Закрой его файрволом (`ufw`, `iptables`) или поставь
> reverse-proxy перед ним. Никогда не вытаскивай админ-API голым в интернет.

## 8. Volumes — где хранятся данные

Контейнеры **эфемерны**: пересоздал контейнер → потерял всё, что было
внутри его файловой системы. Чтобы данные пережили перезапуск, нужны
**volumes** (тома):

```yaml
coordinator:
  volumes:
    - coordinator-data:/app/data   # именованный том → путь в контейнере

volumes:
  coordinator-data:                # объявление тома
```

Docker сам создаёт физическую папку где-то в `/var/lib/docker/volumes/…`.
Ты её не трогаешь руками — управляешь через `docker volume`.

**Что положить в volume:**
- БД (SQLite-файл, Postgres-данные).
- Логи, если хочешь хранить их вне контейнера.
- Загружаемые пользователями файлы.

**Что НЕ класть в volume:**
- Код (он внутри образа).
- Питон-зависимости (тоже внутри образа).
- Конфиги, которые ты потом захочешь поменять — лучше через env-переменные.

### Бэкап тома

```bash
docker run --rm \
  -v vpn-prober_coordinator-data:/data \
  -v $(pwd):/backup \
  alpine \
  tar -czf /backup/backup-$(date +%F).tgz -C /data .
```

Этот трюк («mount volume в одноразовый контейнер») — стандартный приём
для бэкапа. Записывай его как cron-job на host машине.

## 9. Как масштабировать — по шагам

Допустим, ты хочешь проверять ссылки **из 5 разных стран** (DE, US, SG, JP, NL).

**Шаг 1.** На главном сервере (любая страна, лишь бы стабильная) поднимаешь
**только координатор**:

```bash
ssh main-server
git clone … && cd vpn-prober
cp .env.example .env
# В .env:
#   COORDINATOR_API_TOKENS=de-token,us-token,sg-token,jp-token,nl-token
#   COORDINATOR_ADMIN_TOKEN=<длинный-случайный>
docker compose up -d coordinator
```

**Шаг 2.** Закрой админ-порт от мира. На VPS:

```bash
sudo ufw allow from <твой-домашний-IP> to any port 8080
sudo ufw enable
```

Или, лучше, поставь **nginx/caddy** перед координатором с TLS-сертификатом
(Let's Encrypt — бесплатно). Дашборд должен ходить только по HTTPS.

**Шаг 3.** На каждом из 5 «прощупывающих» серверов:

```bash
ssh de-server
git clone … && cd vpn-prober
cp .env.example .env
# В .env только prober-настройки:
#   PROBER_NAME=de-1
#   COORDINATOR_URL=https://coordinator.example.com
#   PROBER_API_TOKEN=de-token
docker compose up -d prober-1
```

Готово. Через минуту в дашборде увидишь 5 проберов. Подаёшь джоб
координатору — он раздаст его по одному из проберов (round-robin по
полу-времени запроса).

**Шаг 4 (опционально).** Если на одной машине хочешь несколько проберов
(чтобы параллелить) — копируй сервис `prober-1` в compose-файле, меняй
`PROBER_NAME`, `PROBER_API_TOKEN` и **обязательно `PROBER_LOCAL_SOCKS_PORT`**
(чтобы sing-box не сталкивался на одном порту).

## 10. Чек-лист продакшен-развёртывания

Когда ты пойдёшь катить это в реальную эксплуатацию, пройдись по списку:

- [ ] **TLS** перед координатором (nginx/caddy + Let's Encrypt).
- [ ] **Firewall**: открыты только 443 (HTTPS) и 22 (SSH). Всё остальное закрыто.
- [ ] **Логи**: `docker compose logs -f` для дебага; в проде — отправляй в
  Loki / Grafana / Datadog. Минимум — настрой ротацию через
  `logging.driver: json-file, options.max-size: 10m`.
- [ ] **Бэкапы**: cron, каждые 6 часов, тарбол volume в S3 / Backblaze.
- [ ] **Мониторинг**: проверяй `/health` каждой минуты через Uptime Kuma
  или Healthchecks.io.
- [ ] **Секреты**: `.env` с правами `chmod 600`, **не в git**.
- [ ] **Авто-перезапуск**: `restart: unless-stopped` (уже стоит в нашем compose).
- [ ] **Обновления**: `git pull && docker compose build && docker compose up -d`.
  Координатор переподнимется за пару секунд — за это время в очередь могут
  накопиться задачи, но проберы их подождут.
- [ ] **CI**: настрой GitHub Actions / GitLab CI, чтобы при каждом коммите
  запускались `pytest` и `ruff`. Образ автоматически билдился в registry
  (GHCR, Docker Hub, AWS ECR).

## 11. Как искать ошибки

DevOps на 80% состоит из «что-то не работает, надо понять что». Порядок:

1. **Проверь, что контейнер вообще запущен:**
   ```bash
   docker compose ps
   ```
   Статус должен быть `Up` (running). Если `Exited` — упал.

2. **Посмотри логи:**
   ```bash
   docker compose logs --tail=200 coordinator
   docker compose logs --tail=200 prober-1
   docker compose logs -f --tail=50    # хвост в реальном времени
   ```

3. **Зайди внутрь контейнера** (если непонятно):
   ```bash
   docker compose exec coordinator bash
   # внутри: ls /app, env, curl localhost:8080/health, etc.
   ```

4. **Проверь сеть между контейнерами:**
   ```bash
   docker compose exec prober-1 curl -v http://coordinator:8080/health
   ```
   Если не отвечает — `coordinator` ещё не стартовал или есть конфликт.

5. **Проверь переменные окружения:**
   ```bash
   docker compose exec prober-1 env | grep -E '(COORD|PROBER)'
   ```
   Если переменная пустая — она не дошла из `.env` (опечатался в имени?).

6. **Проверь, что порт открыт снаружи:**
   ```bash
   curl http://<твой-сервер>:8080/health
   ```
   Если timeout — firewall блокирует. Если `connection refused` — контейнер
   не запущен или не маппит порт.

| Хочу… | Открой файл |
| --- | --- |
| Добавить новый протокол | `prober/parsers/<name>.py` + регистрация в `prober/parsers/registry.py` + тест в `tests/test_parsers.py` |

| Добавить аутентификацию через JWT вместо bearer-токенов | `coordinator/app.py` функции `require_*_token` |
| Изменить дизайн дашборда | `coordinator/templates/dashboard.html` |
| Поднять только пробер (без координатора) | `docker compose up -d prober-1` |
| Снести всё с данными | `docker compose down -v` ⚠️ снесёт том с БД |
| Снести всё, оставив данные | `docker compose down` (без `-v`) |

Если что-то осталось непонятным — спрашивай по конкретному файлу или
команде. DevOps лучше всего учится «починил → понял», поэтому смело ломай
у себя на тестовом сервере и смотри, что произошло.
